1. Vì sao cần agent riêng và agent gồm những gì đã viết

1.1 Lợi ích của agent riêng so với agent dựng sẵn (Claude Code, Codex)

Lợi íchNội dungLưu ý chính xác hóa
1. Tự động hóa không cần người ngồi cạnh Chạy theo lịch hoặc theo sự kiện (commit mới, email đến, dữ liệu đổi), nối vào CI/CD. Công cụ dựng sẵn cũng có chế độ headless (claude -p), chạy trong GitHub Actions và có SDK. Điểm khác của agent riêng: tự điều khiển cách kích hoạt (webhook, hàng đợi, email) và cách xử lý lỗi, không phải bọc bên ngoài.
2. Gắn vào hệ thống riêng Dữ liệu nội bộ, database, API riêng, quy trình riêng đưa thẳng vào tool, kèm quyền do mình quy định (tự chạy / phải hỏi / cấm). Claude Code cũng nối được qua MCP và có phân quyền. Agent riêng kiểm soát được từng lần gọi tool bằng code (ví dụ chặn theo giá trị tham số), không chỉ theo tên lệnh.
3. Kiểm soát dữ liệu và chi phí Quyết định dữ liệu nào đi ra ngoài, dùng model rẻ cho việc đơn giản và model mạnh cho việc khó, ghi log toàn bộ để kiểm toán. Dữ liệu vẫn đến nhà cung cấp LLM khi gọi API. Mình chỉ chọn được cái gì đi ra (lọc, che thông tin nhạy cảm). Muốn dữ liệu không ra ngoài thì phải dùng model chạy local.
4. Thành một phần của sản phẩm Đưa khả năng AI vào ứng dụng hoặc dịch vụ cho người khác dùng thì phải là agent do mình kiểm soát, không thể bắt khách dùng app của hãng. Lý do mạnh nhất. Gói Pro không dùng được cho sản phẩm phục vụ người khác, nên bắt buộc dùng API.
5. Hiểu và gỡ lỗi được Khi agent làm sai, thấy từng bước và sửa đúng chỗ, không phải hộp đen. Claude Code cũng lưu transcript. Agent riêng cho phép gắn tracing và đánh giá tự động vào từng bước.
Cái giá phải trả Phải tự viết và tự bảo trì phần điều phối, an toàn và giám sát. Với việc tương tác hằng ngày như viết code, công cụ dựng sẵn vẫn tốt hơn. Agent riêng đáng làm khi cần ít nhất một trong 5 lợi ích trên.

2. Vòng lặp agent đã viết

2.1 Agent là gì

Agent là chương trình dùng LLM để tự quyết định hành động tiếp theo và thực hiện hành động đó qua tool, lặp lại cho đến khi hoàn thành mục tiêu. LLM chỉ sinh văn bản; phần "hành động" do code của bạn đảm nhận. Vòng lặp là chỗ hai bên gặp nhau.

Mục tiêu / input │ ▼ ┌──────────────┐ gọi API kèm: system prompt + lịch sử + danh sách tool │ Gọi LLM │◄──────────────────────────────────────────────┐ └──────┬───────┘ │ │ phản hồi │ ▼ │ stop_reason == "tool_use" ? │ ├─ Không ──► kết thúc, trả câu trả lời cuối │ └─ Có ──► code chạy tool theo tên + tham số LLM yêu cầu │ │ │ └─► thêm kết quả (tool_result) vào lịch sử ───────┘

2.2 Các thành phần của một vòng lặp

2.3 Cách LLM "gọi" tool

LLM không chạy lệnh. Nó trả về một khối tool_use gồm id, name và input. Code của bạn chạy tool rồi gửi lại một khối tool_result mang đúng tool_use_id đó trong lượt user kế tiếp. LLM đọc kết quả và quyết định bước sau.

2.4 Mã mẫu tối giản (Python, Anthropic SDK)

import anthropic, subprocess

client = anthropic.Anthropic()          # cần ANTHROPIC_API_KEY
MODEL = "claude-haiku-4-5-20251001"
MAX_STEPS = 15

TOOLS = [{
    "name": "git_status",
    "description": "Chạy git status trong repo, trả về đầu ra.",
    "input_schema": {"type": "object", "properties": {}},
}]

def run_tool(name, args):
    if name == "git_status":
        out = subprocess.run(["git", "status", "--short"],
                             capture_output=True, text=True)
        return out.stdout or "(không có thay đổi)"
    return f"Tool không tồn tại: {name}"

def run_agent(goal, system):
    messages = [{"role": "user", "content": goal}]
    for step in range(MAX_STEPS):                      # giới hạn vòng lặp
        resp = client.messages.create(
            model=MODEL, max_tokens=1024,
            system=system, tools=TOOLS, messages=messages,
        )
        messages.append({"role": "assistant", "content": resp.content})

        if resp.stop_reason != "tool_use":             # xong
            return "".join(b.text for b in resp.content if b.type == "text")

        results = []
        for block in resp.content:
            if block.type == "tool_use":
                results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": run_tool(block.name, block.input),
                })
        messages.append({"role": "user", "content": results})

    return "Dừng: quá số bước cho phép"

Giải thích luồng chạy của đoạn mã

Hình dung bạn là thư ký, Claude là sếp ngồi trong phòng kín. Sếp chỉ nói được, không tự đi làm gì. Sếp bảo "xem giúp trạng thái git", thư ký đi xem rồi quay lại báo kết quả. Cứ thế đến khi sếp nói "xong".

Phần của mãLàm gì
MODEL, MAX_STEPSChọn model và đặt tối đa 15 vòng. Đây là cái phanh để agent không chạy mãi và tốn tiền.
TOOLSBản mô tả công cụ gửi cho Claude đọc (tên, công dụng, cần tham số gì). Mới là lời mô tả, chưa chạy gì.
run_toolNgười làm việc thật: nhận tên công cụ, chạy lệnh trên máy, trả kết quả. Công cụ lạ thì báo lỗi, không chạy.
run_agentVòng lặp chính: gọi Claude, xem Claude có xin dùng công cụ không, chạy giúp, ghi kết quả vào sổ rồi gọi lại.
messagesCuốn sổ hội thoại, ghi mọi lời yêu cầu, câu trả lời và kết quả công cụ. Đây là memory ngắn hạn.

Hai điều cần nhớ
  • Claude không tự chạy gì cả. Toàn bộ quyền thực thi nằm ở hàm run_tool do mình viết, nên muốn giới hạn agent thì giới hạn ở đây.
  • Phần "tự quyết định" của agent chỉ là vòng lặp. Muốn thêm kiểm tra an toàn, ghi log hay hỏi người duyệt thì chèn quanh run_tool hoặc giữa các vòng.

3. Tool đã viết

3.1 Tool là gì và gồm mấy phần

Tool là một khả năng hành động mà agent được phép dùng (đọc file, chạy lệnh git, gọi API, truy vấn database). Mỗi tool luôn gồm hai nửa tách biệt:

NửaNằm ở đâuAi dùngVí dụ
Bản khai báo (định nghĩa)Gửi kèm mỗi lần gọi APIClaude đọc để biết có tool gì và cách dùngBiến TOOLS ở mục 2.4
Hàm thực thiCode của mìnhChương trình chạy thật khi Claude xin dùngHàm run_tool ở mục 2.4
Nhớ kỹ Claude chỉ nhìn thấy bản khai báo, không nhìn thấy code bên trong. Khai báo tả sai thì Claude dùng sai, dù hàm thực thi viết đúng.

3.2 Định nghĩa tool bằng JSON schema

Một khai báo có 3 trường bắt buộc: name, description, input_schema. Phần input_schema viết theo chuẩn JSON Schema để mô tả tham số.

{
  "name": "read_file",
  "description": "Đọc nội dung một file văn bản trong thư mục project. "
                 "Dùng khi cần xem code hoặc cấu hình. Không đọc được file ngoài project.",
  "input_schema": {
    "type": "object",
    "properties": {
      "path": {
        "type": "string",
        "description": "Đường dẫn tương đối tính từ thư mục project, ví dụ: src/app.py"
      }
    },
    "required": ["path"]
  }
}

3.3 Viết hàm thực thi

Hàm thực thi nhận tên tool và tham số mà Claude đưa, chạy việc thật và trả kết quả dạng văn bản. Kết quả này sẽ được đưa lại cho Claude đọc (mục 2.3).

from pathlib import Path

PROJECT = Path("D:/V2-Report/ResearchAI-AGENT").resolve()

def read_file(path):
    target = (PROJECT / path).resolve()
    if PROJECT not in target.parents and target != PROJECT:   # chặn thoát ra ngoài project
        return "LỖI: không được đọc file ngoài thư mục project"
    if not target.is_file():
        return f"LỖI: không tìm thấy file {path}"
    return target.read_text(encoding="utf-8")[:20000]         # giới hạn độ dài
  • Trả văn bản, có độ dài giới hạn. Kết quả quá dài sẽ ăn hết ngữ cảnh và tốn token.
  • Một tool một việc. Tool làm quá nhiều việc khiến Claude khó chọn tham số và khó kiểm soát quyền.
  • Không để Claude quyết định điều nguy hiểm. Ví dụ ở trên khóa đường dẫn trong project, thay vì tin tham số path.

3.4 Kiểm tra tham số

Không được tin tham số Claude gửi, vì Claude có thể điền sai hoặc bị dẫn dắt bởi nội dung độc hại trong dữ liệu đọc vào. Luôn kiểm tra trong code trước khi chạy:

Giá trị nằm trong danh sách cho phép (allowlist)Chỉ cho lệnh git status, diff, add, commit; chặn push --force
Phạm vi hợp lệĐường dẫn phải nằm trong thư mục project
Chặn mẫu nguy hiểmKhông nối chuỗi từ Claude thẳng vào lệnh shell. Truyền lệnh dạng danh sách, như ["git", "status"] ở mục 2.4

3.5 Xử lý lỗi trả về cho LLM

Khi tool lỗi, không để chương trình sập. Hãy trả lỗi về cho Claude, kèm cờ is_error, để Claude đọc và tự sửa (thử lại với tham số khác hoặc báo người dùng).

try:
    ket_qua = run_tool(block.name, block.input)
    results.append({"type": "tool_result", "tool_use_id": block.id,
                    "content": ket_qua})
except Exception as e:
    results.append({"type": "tool_result", "tool_use_id": block.id,
                    "content": f"Tool lỗi: {e}", "is_error": True})
  • Thông báo lỗi nên cụ thể và hướng dẫn được: "không tìm thấy file src/a.py, các file có trong thư mục: ..." hữu ích hơn "lỗi".
  • Không đưa vào thông báo lỗi những thứ nhạy cảm (đường dẫn nội bộ, khóa, chuỗi kết nối).
  • Vẫn giữ giới hạn MAX_STEPS, để khi cùng một lỗi lặp đi lặp lại, vòng lặp tự dừng.

3.6 Kết nối MCP

MCP (Model Context Protocol) là chuẩn mở để agent dùng tool do bên khác cung cấp, thay vì tự viết từng tool. Có thể hiểu là "cổng USB" chung giữa agent và các dịch vụ.

4. Điều khiển luồng đã viết

Điều khiển luồng là câu hỏi: ai quyết định bước tiếp theo, và quyết định dựa vào đâu? Có hai cực:

4.2 Lập kế hoạch

Có hai cách để agent biết "làm gì trước, làm gì sau":

Cách làm này tách việc "nghĩ" và "làm", nên có thể chèn một bước người duyệt kế hoạch ở giữa trước khi chạy thật.

4.3 Tự chọn bước

Bước tiếp theo của agent được quyết định ở hai tầng:

  • LLM chọn: mỗi vòng Claude tự quyết định gọi tool nào, hoặc dừng. Đây là mặc định.
  • Code ép hoặc cấm: tham số tool_choice khi gọi API cho phép để LLM tự chọn (auto), bắt buộc phải dùng một tool (tool), hoặc bắt dùng ít nhất một tool (any). Ngoài ra, code có thể chỉ gửi những tool phù hợp với giai đoạn hiện tại (ví dụ giai đoạn "kiểm tra" chỉ có tool đọc, giai đoạn "commit" mới đưa tool ghi vào).

Cách thứ hai giúp thu hẹp quyền theo từng giai đoạn, ít rủi ro hơn là đưa tất cả tool ngay từ đầu.

4.4 Thử lại khi lỗi

Có hai loại lỗi, xử lý khác nhau:

import time

def goi_voi_thu_lai(ham, so_lan=3):
    cho = 1
    for lan in range(so_lan):
        try:
            return ham()
        except Exception as e:
            if lan == so_lan - 1:
                raise                      # hết lượt thì báo lỗi lên trên

            cho *= 2                       # chờ lâu dần: 1s → 2s → 4s

4.5 Đổi hướng

Khi cách làm hiện tại không hiệu quả, agent cần biết chuyển sang cách khác thay vì lặp lại. Có ba mức:

Cần chốt trước tín hiệu để nhận ra "đang đi sai": lặp lại cùng một lệnh nhiều lần, chạm trần số bước, hoặc cùng một lỗi xuất hiện hai lần liên tiếp. Gặp các tín hiệu này thì chuyển sang mức cao hơn.

Điều cần nhớ Điều khiển luồng là sự phân chia trách nhiệm giữa code, LLM và người. Càng nhiều bước đã biết chắc thì càng nên để code lo, càng nhiều tình huống chưa lường trước thì càng cần LLM, và việc rủi ro cao thì giao người duyệt.

5. Memory đã viết

5.1 Vì sao agent cần memory

LLM không tự nhớ gì giữa các lần gọi. Mỗi lần gọi API, model chỉ biết đúng những gì bạn gửi kèm trong lần đó. Cái gọi là "nhớ" là do code của mình lưu lại và gửi lại. Vì vậy memory là một phần phải tự thiết kế.

Memory ngắn hạnMemory dài hạn
Là gìNội dung của cuộc chạy hiện tại: lịch sử messagesThông tin giữ lại giữa các lần chạy, các ngày, các phiên
Nằm ở đâuTrong bộ nhớ chương trình, gửi kèm mỗi lần gọi APIFile, database, kho vector
Giới hạnCửa sổ ngữ cảnh (context window) của modelGần như không giới hạn, nhưng phải tìm đúng thứ cần
Ví dụ trong projectCuốn sổ messages ở mục 2.4state.json, CLAUDE.md

5.2 Giới hạn của memory ngắn hạn

Mỗi vòng lặp, toàn bộ messages được gửi lại, nên sổ càng dài thì:

  • Tốn token hơn (chi phí tăng theo độ dài, và độ dài cộng dồn qua từng vòng).
  • Chạm trần cửa sổ ngữ cảnh: vượt quá thì API báo lỗi.
  • Model dễ bỏ sót chi tiết quan trọng nằm giữa một đống nội dung dài.

Các kết quả tool lớn (nội dung file, đầu ra của test) thường là thủ phạm chính.

def thu_gon(messages, giu_lai=10):

        return messages
    cu = messages[:-giu_lai]
    tom_tat = client.messages.create(
        model=MODEL, max_tokens=500,
        system="Tóm tắt ngắn gọn: mục tiêu, việc đã làm, kết quả, việc còn lại.",
        messages=[{"role": "user", "content": str(cu)}],

Nên phân loại thứ cần nhớ:

  • Trạng thái: việc đang dở, lần chạy cuối, kết quả.
  • Sự kiện đã xảy ra: nhật ký các lần chạy, lỗi đã gặp và cách đã xử lý.
  • Tri thức, sở thích: quy ước commit, repo nào dùng lệnh test nào.

Cho agent tự ghi memory bằng cách đưa vào hai tool, ví dụ doc_memory và ghi_memory. Khi đó Claude tự quyết định điều gì đáng nhớ. Cần kiểm soát bằng code: giới hạn dung lượng, chỉ cho ghi vào thư mục memory, và không cho ghi bí mật (token, mật khẩu).

6.3 Chạy theo sự kiện (webhook)

Webhook là cách một hệ thống khác (GitHub, form, hệ thống thanh toán) gửi một yêu cầu HTTP tới địa chỉ của bạn mỗi khi có chuyện xảy ra. Agent cần một cổng nhận nhỏ luôn mở để đón yêu cầu đó rồi mới gọi agent.

  • Phải xác thực người gửi. Địa chỉ nhận ai cũng gọi được. GitHub ký mỗi yêu cầu bằng một bí mật chung (HMAC), cổng nhận phải tính lại chữ ký và so khớp, sai thì bỏ.

  • Coi nội dung sự kiện là dữ liệu, không phải chỉ thị (ví dụ nội dung commit message do người lạ viết).

6.4 Chạy liên tục (daemon)

Daemon là chương trình luôn chạy nền, chờ việc rồi xử lý, xong lại chờ. Khác với chạy theo lịch ở chỗ chương trình không thoát.

import time

def daemon():
    while True:                         # vòng ngoài: sống mãi

6.5 Hàng đợi

Hàng đợi là chỗ xếp việc theo thứ tự để agent lấy ra làm từng việc. Nó nằm giữa nơi nhận việc (webhook, lịch, người dùng) và agent.

Lợi íchGiải thích
Không mất việcAgent đang bận hoặc sập thì việc mới vẫn nằm đó chờ
Kiểm soát tốc độChỉ cho chạy N việc cùng lúc, tránh vượt hạn mức API và chi phí
Thử lại và xử lý lỗiViệc lỗi quay lại hàng hoặc chuyển sang "hàng chết" để người xem
Tách rờiNơi nhận việc và nơi xử lý có thể chạy ở hai chỗ khác nhau

Với agent nhỏ, hàng đợi có thể chỉ là một bảng trong SQLite hoặc một thư mục chứa các file việc. Khi quy mô lớn mới cần dịch vụ chuyên dụng như Redis hay RabbitMQ.

Hai lỗi hay gặp
  • Hai lần chạy chồng nhau: lịch kích hoạt lần mới khi lần trước chưa xong, dẫn tới hai agent cùng commit. Cần khóa (ví dụ một file khóa, hoặc cấu hình concurrency trong GitHub Actions) để mỗi lúc chỉ một lần chạy.
  • Chạy trùng một việc: webhook có thể gửi lại cùng một sự kiện. Thiết kế việc sao cho chạy hai lần cũng không gây hại (ví dụ kiểm tra "commit này đã xử lý chưa" trong state.json trước khi làm).

6.6 Nhiều agent phối hợp

Thay vì một agent làm tất cả, chia thành nhiều agent nhỏ, mỗi agent một vai, một bộ tool và một bộ rule riêng.

  • Cái giá: tốn token hơn, khó gỡ lỗi hơn (lỗi có thể nằm ở chỗ giao nhận giữa các agent), và có thêm nguy cơ một agent bị dẫn dắt rồi truyền nội dung độc cho agent khác.

7. An toàn đã viết

7.1 Vì sao an toàn là phần quan trọng nhất

Agent khác chatbot ở chỗ nó hành động thật: sửa file, chạy lệnh, push code, gọi API. Một lỗi của agent không chỉ là câu trả lời sai mà là một việc đã xảy ra, đôi khi không hoàn tác được. Các rủi ro chính:

Quyền quá rộngToken GitHub toàn quyền bị dùng để xóa nhánh hay repo khác
Lộ bí mậtToken bị ghi vào log, vào commit hoặc vào prompt

Nguyên tắc nền Đừng dựa vào việc "dặn model đừng làm". Dặn trong prompt là lớp yếu nhất. Các giới hạn quan trọng phải nằm ở code, quyền hệ thống và môi trường chạy, nơi model không thể tự nới ra.

Sandbox là môi trường cô lập để agent chạy bên trong. Nếu agent làm sai hoặc bị dẫn dắt, thiệt hại chỉ nằm trong "hộp" đó.

7.4 Duyệt của người

Với hành động rủi ro cao, để người xác nhận trước khi chạy (human-in-the-loop).

  • Chỗ đặt điểm duyệt: trước khi push lên nhánh chính, deploy production, xóa dữ liệu, chi tiền, gửi tin ra ngoài.
  • Cho người đủ thông tin để quyết: hiển thị đúng diff sẽ commit, đúng lệnh sẽ chạy, không chỉ "agent muốn push, đồng ý không?".
  • Nếu không có người trực (chạy theo lịch ban đêm): đừng bỏ qua bước duyệt. Thay bằng việc agent chỉ push lên nhánh riêng hoặc mở pull request, người duyệt vào ban ngày.
  • Tránh "duyệt cho có": hỏi quá nhiều lần khiến người bấm đồng ý máy móc. Chỉ hỏi ở việc thật sự rủi ro, việc an toàn thì tự chạy.

7.6 Prompt injection

Prompt injection là khi nội dung agent đọc vào (file, trang web, email, commit message, kết quả tool) chứa những câu như chỉ thị, và model làm theo như thể đó là lệnh của chủ. Model không phân biệt tuyệt đối "chỉ thị của chủ" và "dữ liệu cần xử lý", nên đây là rủi ro đặc thù của agent.

7.7 Quản lý bí mật

  • Không để bí mật trong code, prompt hay file cấu hình. Đặt ở biến môi trường hoặc kho bí mật (secret manager, GitHub Secrets), như GITHUB_PAT ở .mcp.json.
  • Token quyền tối thiểu: loại fine-grained của GitHub, chỉ một repo, chỉ quyền cần (ví dụ ghi nội dung, không có quyền quản trị).
  • Đặt thời hạn và quay vòng: token có hạn, thay định kỳ, thu hồi ngay khi nghi ngờ lộ.
  • Không để bí mật chảy vào log: lọc token khỏi log và khỏi nội dung gửi cho LLM.
  • Chặn đọc file nhạy cảm: .env, khóa riêng, file cấu hình chứa mật khẩu nằm ngoài vùng agent được phép đọc.
